# 2.7.0 release plan

Status: **planned**. The current supported and deployed release is `2.6.0` at
commit `2835303b`. This plan covers the next feature release.

## Decision: 2.7.0, not 2.6.1

Use a **minor** bump because the tree since `v2.6.0` adds user-visible
capability, not only fixes:

- level quizzes are now available to learners (API field, visibility rule, and
  the Beginner question banks);
- VPN-only lab sessions now reveal the computed target IP addresses and
  hosts-file mapping.

It also contains two reliability fixes that would justify a patch on their own:
the WireGuard client-pool route and the stale-network cleanup guard. The API
additions are backwards compatible and no database schema change is required,
so a minor release is appropriate and a major bump is not.

## Scope

### Learning

- `GET /api/exercises/tracks/{slug}` returns `has_quiz` per level.
- The level **Quiz** button renders only when the level is complete and an
  active quiz bank exists. The empty-modal path is gone.
- Beginner quiz banks seeded by
  `platform/backend/app/scripts/seed_level_quizzes.py`:

  | Level | Bank | Questions | Pass |
  |---|---|---:|---:|
  | Stage 1 | Beginner Stage 1 Check | 5 | 70 |
  | Stage 2 | Beginner Stage 2 Check | 5 | 70 |
  | Stage 3 | Beginner Stage 3 Check | 4 | 70 |
  | Stage 4 | Beginner Stage 4 Check | 4 | 70 |

- `scripts/ui-learning-smoke.mjs` compares the rendered Quiz and Certificate
  buttons with the track API for every level.

### Labs and network

- VPN-only sessions reveal target IPs and the hosts-file mapping; RangeBox
  sessions keep IPs hidden unless `show_target_ips` is set.
- `scripts/setup-range-server.sh` installs the `10.255.0.0/16 dev wg0` route in
  `PostUp`/`PostDown`; `scripts/fix-wireguard-client-route.sh` repairs existing
  hosts.
- Lab creation preserves networks owned by a session that is still
  `starting`/`running`, so a stop/relaunch no longer removes the live
  environment.

### Operations

- `docs/DEPLOYMENT-RUNBOOK.md` records the pull, rebuild, prebuild, quiz-seed,
  and health commands for both hosts.
- `scripts/status-dashboard.py` reads its host map from
  `docs/status-hosts.json`.
- `scripts/ui-verify-public.mjs` and the event-certificate PDF layout test are
  part of the regression set.

### Capacity and disk baseline

Measured on **11 November 2026** from each deployed backend:

| Host | vCPU | RAM | Computed max | Live cap (75%) | Free disk |
|---|---:|---:|---:|---:|---:|
| Development `172.16.16.44` | 12 | 62 GiB | 20 | **15** | 190 GB |
| Production `172.16.16.41` | 12 | 61 GiB | 20 | **15** | 35 GB |

Both hosts report disk and memory headroom. Disk is the production
constraint: it is above the 10 GB per-launch threshold and the current lab
images are prebuilt, but a new prebuild wave needs space freed first.

## Out of scope

- Quiz banks for tracks other than Beginner. The runtime supports them; the
  content is a separate curriculum task.
- Capacity testing beyond the current single-host sizing evidence.
- New lab images or curriculum changes.
- Database migrations, dependency upgrades, and runtime version changes.
- HA, SSO, multi-tenancy, and other Enterprise work.

## Release gates

All gates must pass before the release commit is tagged:

1. Public CI is green for `RobChaykoski/opencyberrange` (static checks, links,
   docs assets, security headers).
2. Development and production are healthy and both report the expected
   version. `python scripts/status-dashboard.py --config docs/status-hosts.json`
   reports `healthy`.
3. `scripts/ui-learning-smoke.mjs` passes **13/13** on a completed learner and
   **13/13** on a fresh learner.
4. Quiz API and UI: `has_quiz=true` on the four Beginner levels, a 100%
   submission returns the score, and a non-completed level shows no Quiz
   button.
5. VPN-only target reveal and the RangeBox hidden-IP behavior are rechecked on
   both hosts.
6. One non-Beginner lab spawns, reaches `running`, accepts its flag, and is
   stopped and cleaned up.
7. No temporary QA users, lab containers, or lab networks remain on either
   host.
8. Production has enough free disk for the release build (the documented
   prebuild recommendation is 60 GB; `2.6.0` currently has about 35 GB).
9. `docs/status-dashboard.{html,json,md}` and `docs/UI-VERIFICATION.md` are
   regenerated after deployment.

## Release steps

1. Update `versions.yaml`: `platform.version`, all three edition versions,
   `release`, and `development` to `2.7.0`; set the release date.
2. Finalize `CHANGELOG.md`: move the Unreleased entries under `[2.7.0]` with
   the release date.
3. Update `docs/RELEASES.md` with the new tag and its commit.
4. Commit as `release: 2.7.0`, create the annotated tag `v2.7.0`, and push the
   commit and tag to both remotes.
5. Deploy the tag commit to development and production. Production rebuilds
   backend and frontend images (the code is baked in); development copies the
   backend source and rebuilds the frontend.
6. Run `python -m app.scripts.seed_level_quizzes` in each backend container.
7. Update `docs/status-hosts.json` to `expected_version: "2.7.0"`, regenerate
   the dashboard, and record the final evidence.
8. Run the release gates above against the deployed tag.

## Rollback

Redeploy `v2.6.0` (`2835303b`) on the affected host. No schema rollback is
needed: the quiz tables already existed in `2.6.0`, and the seeded rows are
harmless to the older backend. Quiz attempts store the selected option indices
and quiz id, so replacing a question bank keeps historical scores. Avoid
reordering or rewriting a bank's options after learners have attempted it,
because old answer indices would point at different text.
