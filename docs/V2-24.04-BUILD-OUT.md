## Goal

Stand up a clean Ubuntu 24.04 LTS host running the current 2.1.4 development
commit, prove the single-host platform is healthy, and freeze that as the
baseline for the three allowed 2.1.4 workstreams: analytics, reporting, and high
availability.

This is an **update**, not a feature. Do not add product surface during the
build-out.

Two defects found during the gate were fixed in the release branch:

- VPN accepts were inserted into `FORWARD`, where Docker's per-network
  `DOCKER-FORWARD`/`DOCKER` drops hid them after the next network creation.
  The rules now live at the top of `DOCKER-USER`, which Docker does not
  reorder, and duplicate copies from concurrent startup workers are collapsed.
- `x-ocr-network-tap` labs referenced `ocr-network-tap:latest`, but no build
  context existed. `platform/network-tap/` now provides the image, the
  installer builds it, and the tap and GRETAP mirrors share one TC filter so
  both run.
- The installer did not allow the Docker bridge pool to reach the Peer Manager.
  On a UFW-enabled host the backend could not apply VPN rules after a reboot;
  the installer now allows `172.16.0.0/12` to TCP/5000.

## Gate 0 — Access and inventory

Do not start until all of these are true:

- [ ] A sudo-capable SSH user and key (or provider console) is available.
- [ ] The current commit and deployment directory are known.
- [ ] The target has no data that must be preserved.
- [ ] Disk, RAM, CPU, KVM support, and public/private addressing are recorded.
- [ ] Ports 22, 80, 443, 51820/UDP, and optional 5555/TCP are understood.
- [ ] A pre-build snapshot or provider image exists.

Exit: an operator can log in, run `sudo`, and record the inventory.

## Gate 1 — OS baseline

- [ ] Install or reinstall Ubuntu 24.04 LTS.
- [ ] Apply current security updates and reboot.
- [ ] Set UTC, a stable hostname, and correct DNS.
- [ ] Create the non-root administrative user.
- [ ] Confirm OpenSSH, key-only authentication, and the provider firewall.
- [ ] Confirm Docker Engine 24+ and the Compose v2 plugin install cleanly.


Use the current 2.1.4 branch, not an older image:

```bash
git clone https://github.com/RobChaykoski/opencyberrange.git ~/opencyberrange
cd ~/opencyberrange
git log -1 --format='%H %s'
sudo bash scripts/setup-range-server.sh --install
```

Confirm:

- [ ] `ocr-frontend`, `ocr-backend`, `ocr-db`, and `ocr-redis` are healthy.
- [ ] The first-run setup wizard completes with the setup token.
- [ ] `GET /api/version` returns the expected `2.1.4` build.
- [ ] `GET /api/setup/status` reports setup complete.
- [ ] The footer shows the running version.

Exit: the platform is reachable and the build identity is known.

## Gate 3 — Network, firewall, and VPN

- [ ] WireGuard server keys and `wg0` are present.
- [ ] A client config and tunnel work.
- [ ] The platform firewall rules are present:
  - `DOCKER-USER`
  - `FORWARD`
  - `raw PREROUTING`
  - NAT
- [ ] Rules survive a reboot and are re-applied by `ocr-vpn-firewall`.
- [ ] Lab subnets cannot reach the management LAN.
- [ ] One learner cannot reach another learner's `/24`.

Exit: reboot, reconnect, and repeat the isolation checks.

## Gate 4 — Lab and recovery smoke tests

- [ ] Single-container lab.
- [ ] Multi-container lab.
- [ ] Network-tap or capture lab.
- [ ] Shared-container lab.
- [ ] KVM lab on a KVM-capable host.
- [ ] RangeBox, UbuntuBox, and REMnuxBox launch.

KVM readiness check (all three must pass):

```bash
grep -m1 -oE 'vmx|svm' /proc/cpuinfo
ls -l /dev/kvm
docker run --rm --device /dev/kvm alpine:latest test -e /dev/kvm
```

Installing KVM packages inside the guest is not enough. The VM must be started
with a CPU model that exposes `vmx` (Intel) or `svm` (AMD), then fully
power-cycled. On Proxmox, use CPU type `host` and enable nested virtualization
on the host. If the provider does not expose nested virtualization, use a
bare-metal host or mark this node as non-KVM and exclude KVM labs.
- [ ] Database snapshot collection.
- [ ] Restore drill and erasure-ledger re-application.
- [ ] Certificate verification and registration flow.

Exit: the representative lab matrix passes on 24.04.

## Program rules for this build-out

1. No new features. The build-out exists to prove the platform on 24.04.
2. Bug fixes and dependency/security updates are allowed.
3. Analytics and reporting continue in development, but are not treated as
   deployed until Gate 5 passes.
4. Multi-host HA is an Enterprise preview workstream and cannot be added back without a written
   charter amendment.
5. Scoring, SSO, integrations, and other major changes stay in
   [`V3-PARKING-LOT.md`](V3-PARKING-LOT.md).

## Rollback

- Keep the 1.1 line supported on Ubuntu 22.04 and 24.04.
- If 24.04 blocks a 2.1.4 host, rebuild on 22.04 and continue 1.1 maintenance.
- There is no supported in-place downgrade from 24.04. Rebuild is the rollback.
- Preserve the pre-build snapshot and the exact commit reference.

## Definition of done

A new 2.1.4 deployment on Ubuntu 24.04 passes Gates 1–5, reports its version,
survives reboot and restore, and is recorded in the support matrix as tested.
Until then, 24.04 is the target, not a certified baseline.
