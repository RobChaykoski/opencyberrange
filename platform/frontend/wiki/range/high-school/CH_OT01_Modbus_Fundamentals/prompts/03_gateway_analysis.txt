# OT01-L3: Modbus Gateway & Protocol Analysis — Prompt Questions (Planned)

## Gateway Trust Boundary
1. A Modbus TCP-to-SNMP gateway sits between your IT monitoring network and OT PLCs. What additional attack surface does this gateway introduce?
2. How would you validate that the gateway properly filters or modifies Modbus data passing through it?
3. What logging should the gateway maintain to support forensic analysis if a breach is suspected?

## Protocol Anomalies
1. A capture file shows Modbus TCP frames with Unit IDs jumping between 1, 10, and 255. What might this indicate about network segmentation or proxy interference?
2. What function codes are most commonly abused in OT attacks? How would you detect their use in network traffic?
3. How would you distinguish between a legitimate firmware extraction attempt and normal Modbus communication?

## Data Integrity
1. If a register value changes unexpectedly between two consecutive reads (without a write command), what are the possible causes?
2. How would you use checksums or sequence numbers (if available) to validate Modbus response integrity?
3. What role does time-synchronization (NTP/PTP) play in correlating Modbus events across multiple devices?

## Defensive Takeaways
1. Recommend gateway hardening steps (firmware updates, default password changes, rule-based filtering).
2. Describe an IDS rule set for detecting suspicious Modbus function code combinations.
3. How would you network-monitor to detect a "PLC flash" attack attempt (attempting to read/modify PLC firmware via Modbus)?

## Extension: Multi-Protocol Correlation
1. If your OT network runs both Modbus TCP and DNP3 over serial, how would you correlate an alarm in one protocol with evidence in the other?
2. What centralized logging platform would you use to aggregate Modbus, DNP3, and IPMI events?
3. How does time-synchronization (NTP/PTP) affect your ability to correlate events across heterogeneous OT protocols?
